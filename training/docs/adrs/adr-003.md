# Offset-based forecasting and autoregressive rollout

## Status

<!--What is the status? -->

Proposed - 31/07/2026

## Context

<!--What is the issue that we are seeing that is motivating this decision or change?-->

**Tasks in anemoi-training are already offset-based.** `BaseTask` holds
`_input_offsets`, `_output_offsets` and their union `_offsets`, and maps those
relative times to positions in the batch. Every task declares *which* relative
times it reads and predicts through these offsets — this is the common language of
the task layer.

**The forecasting task is special: it is the only current task that performs
autoregressive rollout.** It feeds its own predictions back as inputs and steps
forward in time, so it can forecast arbitrarily far ahead. This is reflected even in
the base class, where `get_output_offsets` is a no-op by default with the note that
"subclasses may override this to shift outputs per rollout step" — the forecaster is
precisely that subclass. Rollout is the defining feature that sets the forecaster
apart from the other tasks.

Until now the forecaster was configured through `multistep_input`,
`multistep_output` and a single `timestep`. This implicitly assumes that inputs and
outputs live on one regular grid of time steps and that the autoregressive rollout
advances by exactly `multistep_output * timestep`. That is too rigid for use cases
such as:

- Inputs and outputs sampled at different frequencies (e.g. read 6-hourly, predict
  3-hourly).
- Irregular input or output times.
- Rollout shifts that differ from the output horizon.

This interface also does not exploit the offset machinery the base task already
provides. Since the base task is already offset-based, the natural way to generalize
the forecaster — and to cover the cases above — is to describe it directly through
input and output offsets plus a rollout shift.

**But arbitrary offsets combined with an arbitrary rollout shift do not, in general, describe a sensible forecaster that can actually be rolled out.** A configuration might read times that are never produced, or forecast the same future time repeatedly across
rollout steps. The question is therefore: *what is the most general forecasting task we admit, and how do we define and check that a given configuration is a valid forecaster?*

## Decision

<!--Describe the change that you are proposing.-->

The decision recorded here is twofold: **a definition of a valid (rollout-able)
forecaster together with a validation scheme that enforces it at construction time**,
and **support for offset-based forecaster configurations in full generality**, as
long as they satisfy the constraints of this definition.

### Definition of a forecaster

We define a forecaster as an **offset-based task** (reusing the `BaseTask` offset
representation) augmented with **autoregressive rollout by a fixed `rollout_shift`
per step**. At rollout step `n` every offset is advanced by `n · rollout_shift`, and
the predictions are fed back as inputs for the next step.

### Validity conditions

A forecaster predicts the future and can do so arbitrarily far ahead through
autoregressive rollout. For a configuration to describe such a forecaster the
following must hold:

1. `input_offsets` contains no duplicates; `output_offsets` contains no duplicates.
2. All input offsets are strictly earlier than all output offsets
   (`max(input_offsets) < min(output_offsets)`).
3. The `rollout_shift` `S` must be strictly positive and such that:
   - **(3a) autoregressive closure** — every shifted input offset lands on a time
     the model already knows, i.e. is contained in the union of input and output
     offsets. Without this the model cannot supply its own inputs at the next
     rollout step.
   - **(3b) no repeated forecasts** — no pairwise difference of output offsets is a
     nonzero integer multiple of `S`, so no future time is forecast more than once
     across rollout steps.

These conditions are the heart of this ADR: they delimit the most general
forecasting task we admit.

Note that training can be restricted to a single rollout step, which raises the
question of why we require the ability to roll out arbitrarily far. The reason is
that a forecaster trained on a single step is typically rolled out over many steps at
inference time; rejecting configurations that cannot roll out prevents users from
training a forecaster they cannot then run. Advanced users who genuinely want an
'invalid' (non-rollout-able) forecaster can bypass the check with
`consistency_check = False` in the task configuration.

### Validation scheme

The conditions are checked at construction (`_validate_offsets` and
`_validate_rollout_shift`), so an invalid forecaster is rejected early with an
actionable `ValueError` rather than failing — or silently misbehaving — later during
training or inference.

- **Inferring `rollout_shift`.** If `rollout_shift` is omitted (defaults to
  `"0H"`) it is inferred as the **largest** valid shift. If no valid shift exists,
  construction fails: such a forecaster cannot be rolled out autoregressively at all.
- **Why `rollout_shift` stays configurable.** In the general offset setting several
  shifts can be valid at once (see *Multiple valid rollout shifts* under Illustrative
  examples). Different valid shifts define genuinely different forecasters — they roll
  out to different future times — so we only infer a sensible default (the largest
  valid shift); the user can still request any valid shift explicitly. This
  is why `rollout_shift` is an explicit config field rather than something we always
  derive.

### How this surfaces in configuration

Because the base task is already offset-based, the definition maps directly onto a
configuration that lists offsets and the rollout shift:

```yaml
task:
  _target_: anemoi.training.tasks.Forecaster
  input_offsets: ["-6H", "0H"]
  output_offsets: ["6H"]
  rollout_shift: "6H"   # optional; inferred if omitted
```

The legacy `multistep_input` / `multistep_output` / `timestep` interface is retained
as a thin translation layer into this offset representation, which is now the single
source of truth. The two styles are mutually exclusive: providing the `multistep_*` /
`timestep` fields forbids the offset fields, and vice versa.

### Advancing the input state (rollout mechanics)

Rolling out one step builds the next input window from the current inputs and the
freshly produced outputs: the new input at offset `o` is whatever state sits at
`o + rollout_shift`, which may be a previous input or a new prediction.

The previous `Forecaster` did this with a tensor `roll()` along the time axis. That
only works when inputs and outputs share one regular grid and `rollout_shift` equals
a whole number of grid positions — advancing is then simply "drop the oldest step(s),
append the newest prediction(s)". With general, possibly irregular offsets this
assumption breaks: "advance by `rollout_shift`" is no longer a constant shift in
index positions, the new inputs are gathered from a non-uniform mix of previous
inputs and predictions, and some states may be dropped or never reused (see
*Irregular offsets* under Illustrative examples). No single `roll()`
expresses this gather.

We therefore precompute an index map (`_advance_map`, with `inin` entries for slots
filled from previous inputs and `outin` entries for slots filled from predictions).
It is derived once from the offsets and `rollout_shift` and reused at every rollout
step.

### Why (3b) — the repeated-forecast condition

Label the outputs of the `n`-th rollout step as `oᵢⁿ = oᵢ + nS`. Two rollout steps
`n` and `m` forecast the same future time when `oᵢⁿ = oⱼᵐ`, i.e.

```
oᵢ + nS = oⱼ + mS   ⟺   oᵢ − oⱼ = (m − n) S
```

So a repeated forecast occurs precisely when some difference of output offsets is a
nonzero integer multiple of `S`. Excluding such shifts guarantees each future time
step is forecast at most once across all rollout steps.

### Illustrative examples

The examples below pair each task configuration with the rollout it produces. Each
rollout diagram is a table whose columns are absolute times on a regular grid (at the
finest spacing that appears in the configuration) and whose rows are rollout steps:
`I` marks an input and `O` marks an output for that step, and a blank cell means that
time is not used at that step. Reading down a column shows how a time is first
forecast (`O`) and then fed back as input (`I`) on later steps.

#### Legacy forecaster

The familiar `Forecaster` behaviour expressed with offsets — the baseline the
offset-based interface must reproduce.

```yaml
input_offsets: ["-6H", "0H"]
output_offsets: ["6H"]
# rollout_shift inferred as 6H
```

| step | -6H | 0H | 6H | 12H | 18H |
| :---: | :---: | :---: | :---: | :---: | :---: |
| 0 | I | I | O |  |  |
| 1 |  | I | I | O |  |
| 2 |  |  | I | I | O |

#### Different input/output frequencies

Inputs and outputs sampled at different frequencies — a case the `multistep_*` /
`timestep` interface could not express.

```yaml
input_offsets: ["-6H", "0H"]
output_offsets: ["3H", "6H"]
# rollout_shift inferred as 6H
```

| step | -6H | -3H | 0H | 3H | 6H | 9H | 12H | 15H | 18H |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 0 | I |  | I | O | O |  |  |  |  |
| 1 |  |  | I |  | I | O | O |  |  |
| 2 |  |  |  |  | I |  | I | O | O |

#### Multiple valid rollout shifts

More than one rollout shift is valid here, which is why `rollout_shift` is exposed in
the config rather than always inferred.

The default case:
```yaml
input_offsets: ["0H"]
output_offsets: ["2H", "3H"]
# rollout_shift inferred as 3H (largest valid shift)
```

| step | 0H | 1H | 2H | 3H | 4H | 5H | 6H | 7H | 8H | 9H |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 0 | I |  | O | O |  |  |  |  |  |  |
| 1 |  |  |  | I |  | O | O |  |  |  |
| 2 |  |  |  |  |  |  | I |  | O | O |

An optional case:
```yaml
input_offsets: ["0H"]
output_offsets: ["2H", "3H"]
rollout_shift: "2H"  # another valid shift, set explicitly by the user
```

| step | 0H | 1H | 2H | 3H | 4H | 5H | 6H | 7H |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 0 | I |  | O | O |  |  |  |  |
| 1 |  |  | I |  | O | O |  |  |
| 2 |  |  |  |  | I |  | O | O |

#### Irregular offsets

Unevenly spaced input offsets — the case that forces advancing to use an index map
instead of a `roll()`.

```yaml
input_offsets: ["-4H", "-2H", "-1H", "0H"]
output_offsets: ["1H", "2H"]
# rollout_shift inferred as 2H
```

| step | -4H | -3H | -2H | -1H | 0H | 1H | 2H | 3H | 4H | 5H | 6H |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 0 | I |  | I | I | I | O | O |  |  |  |  |
| 1 |  |  | I |  | I | I | I | O | O |  |  |
| 2 |  |  |  |  | I |  | I | I | I | O | O |

At step 1 `-2H` and `0H` re-appear in the input but the `-1H` that sat
in between them at step 0 doesn't. A `roll()` on the input of step 0 can only shift a
contiguous block of time positions, so it cannot retain `-2H` and `0H` while
discarding the `-1H` in between. Producing the step 1 input from step 0's inputs and
outputs therefore requires an explicit per-slot gather, which is exactly what
`_advance_map` encodes.

#### Rejected: repeated forecast

An invalid configuration: with this shift the model would forecast the same time
twice, so construction is rejected by condition (3b).

```yaml
# raises ValueError: 3H − 1H = 2H = 2 × 1H is a multiple of the shift
input_offsets: ["0H"]
output_offsets: ["1H", "3H"]
rollout_shift: "1H"
```

| step | 0H | 1H | 2H | 3H | 4H | 5H |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 0 | I | O |  | O |  |  |
| 1 |  | I | O |  | O |  |
| 2 |  |  | I | O |  | O |

The `3H` column holds an `O` at both step 0 and step 2 — the same time is forecast
twice, which condition (3b) forbids.

#### Rejected: no valid rollout shift

A stronger rejection: no shift works at all, so the forecaster can never autoregress
and construction fails regardless of `rollout_shift` (condition (3a)).

```yaml
# raises ValueError: no valid autoregressive rollout shift exists
input_offsets: ["-1H", "0H"]
output_offsets: ["2H"]
```

| step | -1H | 0H | 1H | 2H | 3H | 4H |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 0 | I | I |  | O |  |  |
| 1 |  |  | ? | I |  | O |

The only candidate shift is `2H` (it maps the newest input `0H` onto the output
`2H`). But rolling out by `2H` also requires an input at `1H` — the image of `-1H`,
shown as `?` above — which the model never produces (its only output is `2H`). No
shift lets the model supply its own next input, so the configuration is rejected.

## Scope of Change

<!--Specify which Anemoi packages/modules will be affected by this decision.-->

- anemoi-training

## Consequences

<!--Discuss the impact of this decision, including benefits, trade-offs, and potential technical debt.-->

- We have a precise, shared definition of what constitutes a valid forecaster, and a
  single place that enforces it. This bounds the space of admissible configurations
  and makes the forecaster's rollout semantics explicit.
- Invalid forecaster configurations fail fast at construction with actionable
  messages, instead of surfacing later during training or inference.
- Forecasting configurations become more expressive (mixed frequencies, irregular
  offsets, configurable rollout shift) without new task classes.
- The offset representation becomes the single internal source of truth; the legacy
  `multistep_*` / `timestep` interface is preserved as a thin translation layer.
- The rollout advance is generalised from a fixed `roll()` of the time axis to a
  precomputed index map (`_advance_map`) reused across steps, so it also handles
  irregular offsets where a plain roll would be incorrect.

**Trade-offs:**

- More configuration surface and validation logic to maintain.
- `consistency_check=False` can produce configurations that are not
  autoregressively rollout-able; misuse is possible if the escape hatch is taken
  without understanding the invariants.

## Alternatives Considered [Optional]

<!--List alternative solutions and why they were not chosen.-->

- Introducing a separate `FlexibleForecaster` class rather than extending
  `Forecaster`. Rejected to avoid duplicating task machinery and to keep a single
  offset-based source of truth, with the legacy interface as a translation layer.
- Not validating configurations and leaving correctness to the user. Rejected
  because invalid offset/shift combinations fail in non-obvious ways (unavailable
  inputs during rollout, silently repeated forecasts), and a forecaster's rollout
  semantics are exactly what needs a well-defined, checkable contract.
- Keeping the narrower `multistep_*` / `timestep` interface only. Rejected because it
  cannot express mixed frequencies, irregular offsets, or a rollout shift that
  differs from the output horizon, and it does not reuse the offset-based task layer.
